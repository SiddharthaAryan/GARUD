FROM PROTOTYPE TO HOSPITAL PILOT

The QR identifies the door.
The signed-in phone identifies the nurse.

A shared ward code cannot identify a person by itself. Each officer needs an individually enrolled account on their own phone or a hospital-issued device.

01 · Enrol once

Import the approved 600-person roster. Hospital IT provisions staff identity and roles. Officers sign in once; allow biometric device unlock if supported.

02 · Scan at the door

Entry and exit QRs open a secure link containing ward ID and action. The authenticated session supplies employee ID. Validate the destination and show “Welcome, [name]”.

03 · Update instantly

A server transaction validates the event, closes the last interval, writes an immutable log and updates the current state. The dashboard subscribes to changes.

Recommended implementation

Firebase Authentication + a server-side scan endpoint (Cloud Functions) + Firestore realtime listeners. GitHub holds versioned source; Firebase Hosting serves the app. GitHub Pages is suitable for a static client, but it does not provide authentication, event validation or a database.

Reliable, fair measurement

Use server time, idempotency keys and atomic transactions. Block duplicate entries and mismatched exits. Flag forgotten exits and stale locations; never invent an exit time. Separate scheduled off-duty time, outside-ward intervals, unassigned state and unknown data. A gap between scans is an outside-ward interval: it can include breaks, duties and missed scans, so it must not be labelled travel time.

Protect the workforce

Admins require hospital-approved access; officers see their own history. Deny direct client writes to authoritative events. Use minimal staff data, audit admin access, and agree retention and correction rules with AIIMS IT and nursing leadership. Static QR photos can be scanned remotely; a scan alone does not prove physical presence. Higher assurance requires a ward kiosk, rotating display code or managed-device proximity validation, each with operational tradeoffs.

Useful next features

Shift roster comparison • configurable staffing thresholds • stale-scan alerts • temporary redeployment • officer correction requests • handover notes without patient identifiers • validated coverage reports • aggregated workload patterns. Attendance should use an approved shift clock, rather than infer absence from ward scans.

Before live rollout

Confirm the real ward list and staff roster, staff sign-in method, approved cloud account and hospital IT owner. Pilot two wards first. Test simultaneous scans, forgotten exits, lost phones, access revocation and network outages. Queue offline events as pending and show delayed sync; never present them as current live observations.
